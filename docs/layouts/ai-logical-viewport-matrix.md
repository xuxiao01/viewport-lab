# 17 个逻辑视口：供 AI 执行 H5 适配任务

> 参数事实来源：`apps/web/src/config/viewport-presets.ts`  
> 完整 DPR、代表机型和参数依据见：[多端视口预设参考](./viewport-presets-reference.md)

## 给 AI 的任务说明

以下 17 个值是本项目用于验证 H5 布局的**逻辑视口**，单位均为 CSS px。执行适配、截图、审查或生成测试方案时，应以这些宽高作为 portrait（竖屏）页面的 `viewport.width` 和 `viewport.height`。

它们是验证矩阵，不是 17 个 CSS 断点：先按内容和组件结构设计合理的响应式布局，再使用全部或指定的一组视口回归验证。不要按机型名称写 User-Agent 分支，也不要把截图 PNG 的物理像素尺寸当作 CSS 布局宽度。

```text
目标：页面在下列 CSS 逻辑视口下可用、无非预期横向溢出，文字可读，关键操作可见且可点击。
方向：竖屏。
交互：按移动端、触摸设备处理。
截图：默认只截当前视口，不截整页。
```

## 参数含义与使用规则

### 1. 逻辑分辨率不是物理分辨率

`390 × 844` 的意思是浏览器参与 CSS 布局的宽高是 `390px × 844px`。它不是手机面板的真实像素数，也不是截图文件的必然尺寸。

同一个预设还带有 DPR（设备像素比）。DPR 影响截图清晰度、`window.devicePixelRatio` 和少量基于 DPR 的媒体查询；常规布局宽度、flex/grid、媒体查询和容器查询应基于上表的逻辑 CSS px 判断。

### 2. 平板仍按移动端触摸环境测试

17 个预设均启用移动布局语义和触摸事件模拟：

```ts
{
  isMobile: true,
  hasTouch: true,
  fullPage: false,
  readySelector: '',
}
```

因此平板宽度较大，不代表要模拟桌面鼠标交互。若目标产品另有桌面端需求，应单独建立 desktop 测试矩阵。

### 3. 不要机械创建 17 个断点

正确做法：

1. 先检查页面内容最小宽度、卡片列数、长文本、底部操作区和滚动容器。
2. 只在布局实际发生变化的临界点设置少量媒体查询或容器查询。
3. 在这 17 个逻辑视口中逐一验证结果。
4. 发现问题时修复组件的流式布局或合理断点，不为某一个机型增加专属补丁。

错误做法：

```css
/* 不要为每个预设单独写规则。 */
@media (width: 390px) { /* ... */ }
@media (width: 393px) { /* ... */ }
```

### 4. 验收时优先检查什么

- 页面没有非预期的横向滚动或被裁切内容。
- 标题、正文和按钮文字没有重叠、截断或小到不可读。
- 长标题、动态数据、空状态和错误提示不会撑坏布局。
- 底部固定操作区不会遮挡最后一项内容，点击区域足够大。
- 平板档不会错误沿用窄手机的单列/小字号，也不会出现桌面化后内容过宽。
- 若使用 `cqw`、`cqmin` 等容器查询单位，为旧 WebView 准备非容器单位的回退；是否支持应使用 `CSS.supports()` 检测，而非根据品牌推断。

## 可直接复制给其他 AI 的提示词

```text
请对这个 H5 页面做响应式适配审查与修复。所有尺寸均是 CSS 逻辑像素，按竖屏、移动端触摸环境验证：

390×844、393×852、402×874、430×932、440×956；
820×1180、768×1024、810×1080；
360×800、393×873、420×933；
800×1280、640×876、800×1088、800×1164、720×1100、920×1400。

要求：不要把这些宽度逐一写成媒体查询，也不要按机型或 User-Agent 分支。请先按页面内容设计流式布局与少量合理断点/容器查询，再逐个视口验证。重点检查横向溢出、文字可读性、长内容换行、卡片/表格挤压、固定底部操作区遮挡和触摸点击区域。若使用 cq* 容器查询单位，请提供旧 WebView 不支持时的回退。
```

## 维护规则

- 代码中的 `viewport-presets.ts` 是唯一参数事实来源。
- 修改预设时，同步更新本文档和 `viewport-presets-reference.md`。
- Android 平板部分 DPR 为工程测试值；不能将它视为指定型号的真机认证数据。
